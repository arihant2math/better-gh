# Gap audit (phase 4)
Generated by the bgh-gap-audit workflow against integration da57e58.

## repos-git

The core git hosting works and is well tested. That covers smart HTTP v0/v2 with gzip and partial clone, SSH (keys, deploy keys, LFS authenticate), LFS batch/locks, archives, raw, the contents/git-data/commits/compare APIs, branches, merges, merge-upstream, forks, templates, transfer, rename redirects in the API, topics, languages, contributors, stars, collaborators/invitations, deploy keys, autolinks, classic protection and a basic ruleset engine. The fast code browser is benchmarked. The serious problems are in operations and migration. Admin `gc`/`repack` on a fork parent can delete objects its forks borrow through alternates, which corrupts the forks. Nothing runs maintenance automatically: no auto-gc, commit-graph or bitmaps, and the archive cache is never pruned. There is no importer or mirroring at all, so a GitHub/GitLab migration loses issues and PRs. On security and compatibility: signatures are never verified and required_signatures is not enforced. `internal` visibility behaves exactly like `private`. `refs/pull/*` can be overwritten by pushes. Receive-side fsck is off. There are no org rulesets, no stats/traffic endpoints, no commit comments, and no Deployments or repository_dispatch API. In the web UI the Fork and Watch buttons do nothing, Insights is a placeholder, rulesets have no UI, and old URLs after a rename or transfer spin forever.

### [critical/bug] Admin gc/repack on a fork parent deletes objects its forks borrow (fork corruption)

Forks borrow the parent's objects directly through objects/info/alternates (RepoStore::fork). Admin maintenance runs `git gc --quiet --prune=now` or `git repack -a -d -l` inside the parent, per repo or for every repository via POST /_bgh/admin/maintenance. Example: the parent force-pushes or deletes a branch that a fork still references. Those commits are no longer reachable from the parent's refs, so gc/repack drops them. The fork is left with missing objects, and clone, browse and PR operations on it fail. GitHub avoids this with network-level (shared) object storage and gc that is aware of reachability across the whole network. `--prune=now` also races with in-flight pushes.

*Area:* bgh-admin (maintenance.rs), bgh-git (storage.rs fork model)

*Evidence:* crates/bgh-admin/src/maintenance.rs:348 `"gc" => git(...["gc","--quiet","--prune=now"])`, :350 `["repack","-a","-d","-l","-q"]`; schedule_all at maintenance.rs:162-207 runs it for every repository; crates/bgh-git/src/storage.rs:123-127 says forks borrow objects through objects/info/alternates; crates/bgh-repos/src/forks.rs:9. No check for whether a repository has forks before running gc.

### [critical/missing-feature] No repository/organization import or migration tooling (GitHub/GitLab issues, PRs, metadata)

GitHub offers 'Import repository' (clone from any URL with credentials), the Source Imports API, and GitHub Enterprise Importer / ghe-migrator for full migrations (issues, PRs with review comments, labels, milestones, releases, wikis, user mapping). Here, the only way to bring code in is a manual `git push --mirror`, and everything outside git is lost. That blocks teams moving from GitHub, GHES or GitLab.

*Area:* bgh-repos, bgh-admin, web/src/pages/new

*Evidence:* grep -rniE 'import(er)?_url|source_url|/import|migrations' crates/*/src finds no importer. CreateRepoBody (crates/bgh-repos/src/create.rs:19-41) has no source/clone URL. There are no /repos/{o}/{r}/import or /orgs/{org}/migrations routes, and web/src/pages/new has only NewRepoPage and NewOrgPage.

### [important/missing-feature] No pull mirrors (scheduled sync from external git remotes)

Self-hosters often need read-only mirrors of upstream or vendor repos that refresh on a schedule (GitLab pull mirroring, Gitea mirrors, the old GHES mirror feature). Nothing here fetches from a remote URL, stores mirror credentials, or runs a periodic sync. The GraphQL `isMirror` field is hard-coded false and REST `mirror_url` is always null.

*Area:* bgh-repos, bgh-git, bgh-core registry, web settings

*Evidence:* grep 'mirror' in crates/bgh-repos and crates/bgh-git only hits PR head mirroring (bgh-pulls/src/git.rs mirror_head). crates/bgh-core/src/models/api.rs:544 sets `mirror_url: None`. bgh-core registry.rs has no periodic or cron job API (only job/on_event/service). The migrations have no mirror table.

### [important/bug] `internal` visibility behaves exactly like `private`

On GitHub/GHES, internal repositories are readable by every member of the enterprise (on GHES, every non-suspended user). Here `is_private()` is `visibility != "public"`, and `public_floor` returns None for internal. Only owner, collaborator, team or org-base-permission grants give access. With org base permission `none`, even members of the owning org cannot see an internal repo, which also contradicts the UI text ('Members of {org} can see this repository'). The readable_repos/search filters treat internal as private too. The repo header shows 'Private' for internal repos.

*Area:* bgh-core perms, web RepoLayout

*Evidence:* crates/bgh-core/src/models/db.rs:325 `self.visibility != "public"`; crates/bgh-core/src/perms.rs:100-106 public_floor; perms.rs:498-510 `visibility <> 'public'`; web/src/pages/new/NewRepoPage.tsx:178 description; web/src/pages/repo/RepoLayout.tsx:114 `repo.private ? 'Private' : 'Public'`.

### [important/missing-feature] Commit/tag signatures never verified; required_signatures not enforced; no SSH signing keys

Every signed commit is reported as `verified:false, reason:unknown_key`, so the web commit page labels every signed commit 'Unverified'. There is no GPG or SSH signature verification against users' GPG keys (the /user/gpg_keys API exists but is unused for verification). There is no /user/ssh_signing_keys API. Classic and ruleset `required_signatures` are stored but silently not enforced on push or merge. Commits made on the server (web edits, merges, template generation) use --no-gpg-sign rather than a web-flow signing key, so they cannot be shown as Verified either.

*Area:* bgh-repos (gitjson, protection), bgh-accounts (gpg/ssh signing keys), bgh-git, web commits

*Evidence:* crates/bgh-repos/src/gitjson.rs:66-90 Verification::for_signature always verified:false; crates/bgh-pulls/src/commits.rs:153 'unknown_key'; docs/packages/repos-api.md Known gaps; protection.rs check_classic/check_ruleset never read required_signatures; grep ssh_signing_keys finds nothing; crates/bgh-git/src/write.rs:174, ops.rs:713, merge.rs:209 '--no-gpg-sign'; web/src/pages/commits/CommitPage.tsx:117.

### [important/perf] No automatic git maintenance: gc disabled, no commit-graph/bitmaps, archive cache never pruned

Every repo is created with gc.auto=0 and receive.autogc=false, and receive.unpackLimit=100 keeps every large push as its own pack. Nothing schedules gc, repack, commit-graph or bitmap writes; the only automatic task is pack-refs. Over time repos build up hundreds of packs and loose objects. Without bitmaps, clones and fetches of large repos are CPU-heavy. Without commit-graph, history, merge-base, ahead/behind and last-commit walks run slower. On top of that, the archive cache (`{data_dir}/cache/archives`) grows without bound because `prune_cache` is never called. Maintenance is manual only, through the admin endpoint, which is itself unsafe for fork parents.

*Area:* bgh-git storage/maintenance, bgh-repos jobs, bgh-core registry

*Evidence:* crates/bgh-git/src/storage.rs:11-24 REPO_CONFIG (`autogc = false`, `unpackLimit = 100`, `[gc] auto = 0`); crates/bgh-core/src/registry.rs has only job/on_event/service (no periodic scheduling); grep 'commit-graph|bitmap' in crates finds nothing that writes them; crates/bgh-git/src/archive.rs:221 prune_cache has no callers; git-transport.md Known gaps.

'coming soon'`.

### [important/partial-feature] Rulesets incomplete: no org rulesets, limited rule types, no UI, so wildcard protection is unreachable from the web

Only repo-level rulesets exist. /orgs/{org}/rulesets (org-wide rules across repos with repository_name conditions) is missing, as are rule-suites/insights. Supported rule types are only creation, update, deletion, required_linear_history, required_signatures (not enforced), non_fast_forward, pull_request and required_status_checks. Missing are the push rules (file_path_restriction, max_file_size, file_extension_restriction, max_file_path_length), the metadata rules (commit_message_pattern, commit_author_email_pattern, committer_email_pattern, branch_name_pattern, tag_name_pattern), merge_queue, required_deployments and workflows. Bypass actor types DeployKey and Integration are rejected. The web has no ruleset editor, and the classic protection UI says 'Classic rules protect one existing branch. Use rulesets for wildcard patterns', so wildcard protection such as release/* and tag protection are reachable only through the raw REST API. The `evaluate` mode is stored but has no effect or reporting.

*Area:* bgh-repos rulesets/protection, bgh-accounts orgs, web repo-settings

*Evidence:* crates/bgh-repos/src/rulesets.rs:40-49 RULE_TYPES, :311 allowed actor types; grep '/orgs/{org}/rulesets|rule-suites' finds nothing; web/src/pages/repo-settings/RepoSettingsPage.tsx sections (no rulesets); BranchesSettings.tsx:217 hint text; protection.rs:210 loads only enforcement='active'.

### [important/security] refs/pull/* (and other internal refs) writable by git push and the refs API

GitHub hides refs/pull/* from receive-pack ('deny updating a hidden ref'). Here, any user with Write can push to, force-update or delete refs/pull/N/head and refs/pull/N/merge, over HTTP or SSH, or create them with POST /git/refs. That lets them tamper with or break the PR heads and merge refs that bgh-pulls and Actions checkout depend on. A `git push --mirror` from a GitHub clone also overwrites them. No receive.hideRefs or transfer.hideRefs is configured, and authorize_push or write_ref do not check the namespace.

*Area:* bgh-git smart_http/storage, bgh-repos git_http/refs/gitdb

*Evidence:* crates/bgh-git/src/storage.rs:11-24 REPO_CONFIG has no hideRefs; grep 'refs/pull' in bgh-repos/src (git_http.rs, protection.rs, refs.rs, ssh/exec.rs) returns nothing; gitdb.rs:762-768 create_ref only validates the ref name syntax; bgh-actions/src/runner/checkout.rs:226 checks out refs/pull/*.

### [important/security] Pushed objects are not fsck'ed

receive.fsckObjects and transfer.fsckObjects are not enabled, so the server accepts and redistributes malformed objects. That includes the malicious .gitmodules/symlink trees that git's server-side fsck blocks (e.g. CVE-2018-11235-class attacks). GitHub runs fsck on push.

*Area:* bgh-git storage/smart_http

*Evidence:* crates/bgh-git/src/storage.rs:11-24 REPO_CONFIG has no fsckObjects; grep fsckObjects in crates finds nothing.

The repo header Fork and Watch buttons have no onClick, so a fork cannot be created from the UI. Watch settings open only from the command palette. There is no forks/network page, no 'forked from X' line, no 'Sync fork' button (even though POST /merge-upstream exists), and no 'Use this template' button on template repos (only /new?template_owner=… works if the user knows about it). Stargazers and watchers lists also fall through to the placeholder page.

### [important/bug] Old web URLs after a repo rename/transfer show an endless spinner instead of redirecting

The API and git resolve old names through repo_redirects, but the web RepoLayout looks the repo up by the URL's owner/name in the sync store. For an old name, getRepository() succeeds (the redirect resolves to the new repo) and ensureScope returns true, but repoByName(oldOwner, oldName) never matches. The status stays 'loading', so the user sees a spinner forever and is never sent to the new URL. Links in issues, chat and bookmarks break after every rename or transfer.

*Area:* web/src/pages/repo/RepoLayout.tsx, web sync selectors

*Evidence:* web/src/pages/repo/RepoLayout.tsx:38-54 (state only set to 'missing' on failure, no redirect on success), :57-71; web/src/sync/selectors.ts:8-9 repoByName keyed by fullName; crates/bgh-core perms RepoAccess::load redirect fallback (repos-api.md).

### [important/api-incompat] GraphQL branch protection rules and createCommitOnBranch missing (Terraform/bot compatibility)

The latter makes signed, server-side commits and is used by changesets, release-please and similar bots. ### [important/missing-feature] No CODEOWNERS validation

GitHub exposes GET /repos/{o}/{r}/codeowners/errors and highlights invalid CODEOWNERS lines (unknown users/teams, users without write access, bad syntax) in the file view. Here CODEOWNERS is parsed only to request reviews in bgh-pulls. Typos fail silently, so required code-owner reviews never trigger.

### [important/ops] LFS storage bypasses quotas; no per-file push size limit

check_push_quota sums only repositories.size, so LFS uploads (counted in lfs_size) are unlimited. A single user can fill the disk with LFS. Git pushes have no per-file limit either (GitHub rejects files over 100 MB with GH001 and warns above 50 MB) and no receive.maxInputSize, so one huge push is accepted before the quota check applies on the next push.

*Area:* bgh-core settings, bgh-repos lfs, bgh-git

*Evidence:* crates/bgh-core/src/settings.rs:509-534 (uses repo.size and sum(size) only); grep quota in crates/bgh-repos/src/lfs returns nothing; grep 'maxInputSize|GH001|max_file_size' in crates returns nothing; git-transport.md: 'no per-repo quota enforcement'.

### [important/missing-feature] Deleted repositories cannot be restored; transfers to users unsupported

DELETE /repos/{o}/{r} hard-deletes the row and enqueues storage removal. GitHub (and GHES site admin) can restore deleted repos for 90 days, and an accidental delete here is unrecoverable. Transfers to another user (which require that user's acceptance on GitHub) return 403 because there is no pending-transfer flow.

*Area:* bgh-repos, bgh-admin

*Evidence:* crates/bgh-repos/src/repos.rs:29-60 `DELETE FROM repositories WHERE id = $1`; no deleted_at or restore in repos.rs or crates/bgh-admin/src/manage_repos.rs; crates/bgh-repos/src/settings.rs:407-414 forbidden unless the caller can create in the target; repos-api.md Known gaps.

## issues-projects

The core issue tracker is solid and mostly matches GitHub. bgh-issues has REST for issues, comments, reactions, labels, milestones, assignees, lock, transfer, timeline, sub-issues and pins. The web UI covers the list, timeline, issue forms, labels and milestones, all synced locally with optimistic updates. Projects v2 (table, board and roadmap views, custom fields, iterations, simple workflows) and a git-backed wiki are in place, but only through private /_bgh endpoints. The biggest problems for a team moving from GitHub are: 1) there are no image or file attachments; 2) "Fixes #n" in a PR description does not close the issue on merge; 3) the GraphQL ProjectV2 API is a stub that returns empty results, and there is no Projects REST API. Discussions and Gists are not implemented at all (Gists are only advertised in URLs and scopes), and issue types and issue dependencies (blocked by / blocking) are missing. The client-side Markdown renderer (marked) is much weaker than the server's comrak renderer: no alerts, no footnotes, 18 emoji, no SHA or cross-repo links, no custom autolinks, and no Mermaid or math in either renderer. Several common GitHub actions are missing from the UI: issue Subscribe, Development / linked PRs, the Projects sidebar, hiding comments, deleting issues, and ticking task-list checkboxes. Projects lack insights, per-project roles, converting drafts to issues, and project and wiki webhooks.

### [critical/missing-feature] No image/file attachments in issues, comments, PRs or wiki

On GitHub you paste or drop screenshots and logs into any comment and they upload to user-attachments. Here there is no upload endpoint and no attachment storage. The editor intercepts paste/drop and shows the toast 'File uploads are not supported yet'. Bug reports with screenshots are a core issue flow.

*Area:* bgh-core/bgh-server (new uploads storage + route), web/src/components/editor

*Evidence:* web/src/components/editor/MarkdownEditor.tsx:81 ('Image paste/drop needs an upload endpoint, which the server doesn't have yet') and :239 (toast). docs/packages/issues-web.md 'Known gaps': no POST /_bgh/uploads. grep 'upload' in crates/* only finds release assets (bgh-releases) and git-upload-pack.

### [critical/bug] Closing keywords in PR description don't close issues on merge

On GitHub, 'Fixes #12' in a PR body links the PR (Development section) and closes the issue when the PR merges into the default branch. Here only commit messages pushed to the default branch are scanned (refs.rs listener on Event::Push). Nothing handles PullRequestMerged for closing refs. With the default merge settings the merge commit message is the PR title (merge) or the commit list (squash), not the body, so the issue stays open. There is also no 'closed by PR' timeline event and no 'connected' event.

*Area:* bgh-issues (refs listener), bgh-pulls merge

*Evidence:* crates/bgh-issues/src/refs.rs:238 closing_refs is only used at refs.rs:334 in the Push listener. grep closing_refs/PullRequestMerged: no listener in bgh-issues. crates/bgh-pulls/src/merge.rs:96-140 builds the message from title/commits unless merge_commit_message == PR_BODY. GraphQL closedByPullRequestsReferences (crates/bgh-graphql/src/model/issue.rs:398) is a body heuristic only.

### [critical/api-incompat] Projects v2 API missing: GraphQL ProjectV2 is an empty stub, no REST

GitHub Projects automation (gh project *, actions/add-to-project, scripts using addProjectV2ItemById / updateProjectV2ItemFieldValue, the projectsV2 REST API) has nothing to call. Repository.projectsV2, User/Organization.projectsV2 and Issue.projectItems always return empty connections. There are no ProjectV2 mutations. createIssue silently ignores projectV2Ids, so `gh issue create --project` cannot work. Projects are only reachable through private /_bgh/projects routes. Because the stubs return empty data instead of errors, scripts will wrongly conclude that no projects exist.

*Area:* bgh-graphql, bgh-projects

*Evidence:* crates/bgh-graphql/src/model/misc.rs:348-354 empty_connection!(ProjectV2Connection / ProjectV2ItemConnection). model/repo.rs:541-550, model/actor.rs:174-183, model/issue.rs:265-273 return the stub. mutation/issues.rs:69 project_v2_ids is never read in create_issue (lines 413-450). crates/bgh-projects/src/lib.rs routes are all /_bgh/*. docs/packages/projects-wiki.md 'Known gaps' admits no REST/GraphQL Projects v2 API.

GitHub Discussions (categories, Q&A answers, polls, announcements, upvotes, convert issue to discussion, GraphQL discussion API, discussion webhooks) do not exist. Only the repo flag has_discussions is stored, and the settings UI exposes a toggle that does nothing. There are no /gists REST endpoints, no gist git repos, and no UI (create, list, star, fork, revisions, comments, secret gists, clone over HTTP). The API still advertises gists_url, public_gists_url and starred_gists_url, and the 'gist' OAuth scope can be granted, so clients follow links that 404.

### [important/missing-feature] Issue types (org-level Bug/Feature/Task) missing

GitHub issue types (org-defined types, the issue 'type' field in REST, the type: qualifier, type in issue forms and templates, the issueType GraphQL field, the issue_type_added timeline event) are absent. Templates parse `type:` but it is never applied. GraphQL createIssue/updateIssue accept issueTypeId and silently ignore it.

## pulls

The PR backend (crates/bgh-pulls) is broad and mostly GitHub-shaped. It covers the full REST surface for pulls, reviews, review comments (multi-line, file-level, replies), requested reviewers, statuses and checks. It also handles merge, squash and rebase without a work tree, auto-merge, CODEOWNERS, classic branch protection, synchronize/outdated remapping, and draft and thread resolution through /_bgh. The web client has a virtualized split/unified diff, a file tree, pending reviews, single suggestions, a merge box and a checks tab. The serious problems are in the merge-governance and linking flows. Closing keywords in the PR body never close issues on merge. Rulesets (pull_request, required_status_checks, required_signatures) are ignored when a PR is merged. Statuses posted to a fork's repo can satisfy, or override, the base repo's required checks. Several GitHub workflows that teams depend on are absent end to end: merge queue, the deployments API, signature verification, a revert button, conflict resolution, rebase update-branch, diff context expansion and syntax highlighting, and batch suggestions. Smaller gaps are UI controls with no entry point (review dismissal, base change), no linked-issues sidebar, a thin PR creation form, timeline and GraphQL items missing for tooling, and a handful of UX bugs in the merge box and timeline.

### [critical/missing-feature] Closing keywords in PR body ("Fixes #N") do not close issues when the PR is merged

On GitHub, merging a PR into the default branch closes every issue that the PR body references with a closing keyword, or that is manually linked. Here, issues are closed only by closing keywords in commit messages pushed to the default branch (bgh-issues refs::on_event on Event::Push). Nothing listens to PullRequestMerged to close the issues referenced in the PR body. The default merge commit message is the PR title (merge) or the commit list (squash), so the body is never scanned unless the repo setting is PR_BODY. GraphQL closingIssuesReferences parses the body for display only. closing_refs also ignores the owner/repo#N and URL forms.

*Area:* bgh-pulls merge / bgh-issues refs

*Evidence:* crates/bgh-issues/src/refs.rs:238-345 (closing_refs only used in commit_refs for Event::Push, is_default); grep for PullRequestMerged listeners: only bgh-notify, bgh-search, bgh-projects (no issue closing); crates/bgh-pulls/src/merge.rs:96-143 (default messages exclude body); crates/bgh-graphql/src/loaders.rs:398 closing_numbers used only for the read field.

### [critical/security] Repository rulesets are ignored when merging PRs (pull_request, required_status_checks, required_signatures rules)

bgh-repos stores rulesets with pull_request rules (required_approving_review_count, require_code_owner_review, required_review_thread_resolution, require_last_push_approval, dismiss_stale_reviews_on_push) and required_status_checks rules. For pushes, these rules only block direct pushes. bgh-pulls merge, mergeability and auto-merge read only the classic branch_protections table (protection::rules_for) and never call bgh_repos::protection::check_update or read repo_rulesets. A ruleset that requires 2 approvals and green CI therefore does not block a PR merge. Teams migrating from GitHub, where rulesets are now the default governance tool, would silently lose enforcement.

*Area:* bgh-pulls protection/merge/mergeability/automerge

*Evidence:* crates/bgh-pulls/src/protection.rs:57-125 (SELECT ... FROM branch_protections only); grep 'ruleset|RepoRules' in crates/bgh-pulls/src -> no matches; crates/bgh-repos/src/rulesets.rs:39-48,228-247 (pull_request params stored); crates/bgh-repos/src/protection.rs:396 (pull_request rule only rejects direct pushes).

### [critical/security] Statuses and check runs on the head fork can satisfy or override required checks on the base repo

check_outcomes queries commit_statuses and check_runs WHERE repo_id = ANY([base, head_fork]) and picks the latest row per context/name (DISTINCT ON ... ORDER BY id DESC). Anyone who forks the repo has write access to their fork, so they can POST /repos/{fork}/statuses/{sha} with context 'ci' state=success after the base repo's CI posted 'failure'. Their newer row wins and the required check passes, which defeats branch protection. Required checks also ignore checks[].app_id (expected source), so any integration can satisfy a check by name.

*Area:* bgh-pulls protection

*Evidence:* crates/bgh-pulls/src/protection.rs:266-273 (repo_ids includes head_repo_id), 136-189 (DISTINCT ON (context) ... ORDER BY context, id DESC across both repos); checks[].app_id never read (protection.rs:110-121 reads only context).

*Area:* bgh-pulls, bgh-repos rulesets, bgh-actions (merge_group), web MergeBox

## accounts-orgs

The basics are solid and checked against the code: password and OIDC login, TOTP 2FA with recovery codes, sessions, classic PATs, OAuth apps (code + PKCE + device flow, gh CLI seeded), SSH/GPG keys, user and org blocks, orgs with members, invitations, outside collaborators and base permission, and nested teams with inherited grants. bgh-accounts and bgh-admin expose these with GitHub-shaped REST and a matching settings/org-settings UI. The biggest gaps are for integration and enterprise adoption. GitHub Apps do not exist at all: no JWT, no installation tokens, no per-app webhooks or permissions. There is no LDAP, SAML, SCIM or IdP team sync, no WebAuthn/passkeys, no fine-grained PATs and no custom or organization roles. Several existing flows are broken or unenforced. Invitees have no web page to accept org or repo invitations, and the email link goes to an unrouted page. The admin's "disable password login" setting is not enforced. Org 2FA requirement can't be set or enforced. Blocking affects only follows and org invitations. Internal repos behave like private ones. Account renames create no redirects. Profile features (contribution graph, pinned repos, status, profile README) and self-service rename/deletion are missing.

### [critical/missing-feature] GitHub Apps entirely missing (app registration, manifests, JWT auth, installation tokens, per-app webhooks/permissions)

GitHub Apps are how most bots and integrations authenticate (CI bots, Renovate, Probot, Jira/Slack connectors, actions/create-github-app-token, Terraform with app auth). GitHub provides: /settings/apps registration and the app-manifest flow; RS256 JWT auth for GET /app and /app/installations; POST /app/installations/{id}/access_tokens (ghs_ tokens with fine-grained permissions and a repo list); /installation/repositories; /user/installations; /orgs/{org}/installations; installation and installation_repositories webhooks; a per-app webhook URL and secret; ghu_ user-to-server tokens; and bot users ({slug}[bot]). None of this exists here. Check runs are attributed to two hardcoded fake apps ('actions' and 'Better GitHub API'), and the auth layer only knows PATs, OAuth tokens, Basic auth and sessions.

*Area:* bgh-accounts, bgh-core auth, bgh-notify webhooks, bgh-pulls checks; web settings (no /settings/apps)

*Evidence:* No routes match '/app', '/app/installations', '/apps/{' or 'installation' anywhere in crates/*/src lib.rs routers (grep). crates/bgh-pulls/src/checks.rs:102-130: app_json() hardcodes ids 1 and 2. crates/bgh-core/src/auth.rs:1-11 and 132-140: only token/bearer (PAT/OAuth hash lookup), basic and cookie; no JWT. migrations/0001_accounts.sql: access_tokens.kind allows 'app' but nothing uses it. crates/bgh-notify/src/webhooks/mod.rs:72-74 lists 'installation*' event names but nothing emits them. crates/bgh-accounts/src/oauth.rs:1637 returns "installation": null.

## notify-search-activity

Most of the surface is in place: the notifications REST API, thread and repo subscriptions with custom watching, per-reason web and email settings, threaded emails with one-click unsubscribe, repo and org webhooks (CRUD, ping, test, delivery log, redelivery, HMAC signatures, SSRF guard), a site-admin global hook CRUD, all seven /search endpoints, the Events API family and a local-first inbox with keyboard triage. The weak point is event wiring. Several webhook and activity mappings listen for event variants that no crate emits, or skip variants that crates do emit. As a result, star/watch, release edited, member removed/edited, repository archived/publicized/transferred, Checks-API check_run/check_suite, and team/membership/org-member webhooks never fire. The whole pipeline also rides a best-effort in-process broadcast bus that drops events when a listener lags or the process crashes. On the feature side, teams moving from GitHub would miss reply-by-email, Atom feeds, auto-watching repos they get access to, Saved and Done inbox views, conditional requests (ETag/If-Modified-Since, X-Poll-Interval) for polling clients, a delivery log for global hooks, and the review:/status:/team-review-requested:/linked:/project: issue-search qualifiers. There is also one privacy defect: notification rows (and later title changes) keep syncing to users after they lose access to a private repo.

## actions-packages-security

Actions is the only part of this domain that has been built, and it is substantial. bgh-actions has a validating workflow parser, a full `${{ }}` expression engine, matrix/needs/outputs, workflow-level concurrency, re-runs, artifacts, secrets and variables at repo/org/env level with sealed boxes, live SSE logs, check-suite integration, and a good web UI (virtualized logs, run graph, dispatch). It falls short in the areas teams depend on most. Reusable workflows hard-fail. Environments have no protection rules or approvals, and there is no Deployments API. The cache is a no-op and there is no toolkit runtime, cache or OIDC endpoint. Runners only work through the custom `bgh-runner` protocol, which reports Linux/X64 no matter the machine. Several triggers are parsed but never fired (`workflow_run`, `repository_dispatch`, PR `labeled`/`ready_for_review`, reviews). The `GITHUB_TOKEN` ignores `permissions:` and acts as the triggering human, with no protection against workflows triggering themselves in a loop. There are also two bugs: the README status badge has no route, and Re-run from the PR Checks tab leaves the check stuck in queued. Packages are completely absent: no container/OCI registry and no npm, Maven, NuGet, RubyGems or Cargo. Security features are also completely absent: no Dependabot, code scanning/SARIF, secret scanning or push protection, advisories or dependency graph. Only webhook event names and GraphQL stubs that return false/null exist, and the visible repo Security tab is a "coming soon" placeholder.

### [critical/missing-feature] No container (OCI/Docker) registry

GitHub ships ghcr.io / GHES containers registry (OCI distribution v2 API: /v2/ manifests, blobs, chunked uploads, token auth via PAT or GITHUB_TOKEN with packages:write, plus /user|orgs/{org}/packages REST and a Packages UI). Teams that push images from CI (docker/login-action + build-push-action) to the forge registry have nowhere to push. Nothing exists here.

*Area:* new crate (e.g. bgh-packages), bgh-server router, bgh-core perms/scopes, web (repo/org/user Packages tabs)

*Evidence:* No /v2 or /packages route in any crate (grep 'route("/v2|"/v2|/packages' crates → none). bgh-server/src/lib.rs merges only accounts, repos, issues, pulls, notify, releases, search, admin, sync, graphql, actions, projects, wiki. No migration for packages in migrations/ (0001..1200). The only trace is the scope icon mapping in web/src/pages/auth/consent.tsx:41 (':packages').

## admin-ops

The site-admin surface is broad and mostly real. bgh-admin registers the GHES admin REST endpoints (users, suspend/promote, impersonation tokens, keys, global hooks, stats, license, announcement, org and enterprise audit logs) plus a full /_bgh/admin API for users, orgs, repos, quotas, jobs, health, maintenance and settings, and the lazily loaded /site-admin web UI covers all of it. The weak side is operations and security. There is no Prometheus/OTel endpoint, no JSON logs, no HA story, no Helm chart, no backup tooling beyond pg_dump+tar, and no GitHub/GHES importer. Several defaults or settings are unsafe or have no effect: the built-in Actions runner falls back to a host shell that inherits DATABASE_URL, the password_login=false toggle is never enforced, the admin "gc" runs --prune=now on fork parents that use alternates, there is no private mode, and git HTTP password auth is not throttled. Housekeeping is missing (no scheduled repo repack, the archive cache is never pruned), the event bus drops events on SIGTERM, and SELF_HOSTING.md is stale (it says SSH is not shipped) and leaves out Actions and about 20 env vars. Audit logging covers most web writes but has no git events, no Actions secrets or runner changes, no attribution of actions taken with impersonation tokens, and no streaming.

### [critical/security] Built-in Actions runner defaults to a host shell executor that inherits the server's secrets

GHES never runs workflow code on the appliance; jobs run on separate runners. Here BGH_ACTIONS_BUILTIN_RUNNER defaults to true and BGH_ACTIONS_EXECUTOR to 'auto', which picks the shell executor whenever docker is unavailable. That is the case in the shipped Dockerfile/compose image (no docker binary or socket). Shell steps are spawned with the inherited process environment (env_clear is never set), so any user who can push a workflow file (including self sign-ups, which are enabled by default) can read DATABASE_URL, REDIS_URL, BGH_SMTP_URL, BGH_ACTIONS_SECRET_KEY and the data dir, then make themselves site admin or read every repo. ### [critical/bug] Admin 'gc' maintenance runs `git gc --prune=now`, which can corrupt forks and race with pushes

Forks are `clone --shared` and borrow objects from the parent through objects/info/alternates. Running gc --prune=now on a parent deletes objects that are unreachable from the parent's refs but still reachable from forks' refs (for example after a force-push or branch delete in the parent), which corrupts the forks. --prune=now also has no grace period, so objects from an in-flight receive-pack that are not yet referenced can be pruned (git's documented hazard). POST /_bgh/admin/maintenance can run it on every repo at once. It also breaks the backup guarantee in SELF_HOSTING.md that 'git objects are only ever added'. GitHub uses a long expiry and fork-network-aware repacks.

*Area:* bgh-admin maintenance, bgh-git, docs

*Evidence:* crates/bgh-admin/src/maintenance.rs:348 `"gc" => git(state, &dir, &["gc", "--quiet", "--prune=now"])`; crates/bgh-repos/src/forks.rs:8-10 (forks use alternates); docs/SELF_HOSTING.md Backup section ('automatic gc is off'); lib.rs:160 schedule_all

## web-ux-perf

The web client has a solid Linear-style base. It has a local-first MobX pool persisted to IndexedDB, WebSocket deltas with backoff and replay, optimistic mutations with rollback, per-route lazy chunks, data prefetch on hover and focus, and virtualization for issue lists, diffs, code, logs and admin tables. It also has a service-worker app shell, inlined boot data, hashed and precompressed immutable assets, Inter font preload, an enforced bundle budget (current initial JS is about 130 KB gzip), and good keyboard and command-palette coverage. The page set is broad and covers issues, PRs, Actions, projects, wiki, releases, branches, tags, commits, blame, compare, user, org and repo settings, and site admin. The biggest adoption blockers are: no way to accept repo or org invitations in the web UI, no repository import despite a `/new/import` route, dead Fork and Watch buttons, Security and Insights tabs that are "coming soon" placeholders, and many GitHub URLs the backend emits that land on placeholder or not-found pages. On quality, the client Markdown renderer diverges from the server's (no alerts, autolinks or highlighting), there are no attachment uploads, diffs have no syntax highlighting or context expansion, deep links to comments don't scroll, and unsent comment drafts are lost on navigation. On performance, REST-backed pages (code, commits, releases, Actions, settings) use a memory-only cache, so they are not local-first across reloads. Bootstrap loads every issue of every accessible repo before the app renders. Issue and PR timelines are neither virtualized nor memoized. The layout shell has no mobile breakpoints, and SPA navigations are not announced to assistive tech.

## api-compat

The cross-cutting REST plumbing is solid. Errors use GitHub's shape (message, documentation_url, status, errors[]). Pagination goes through bgh_core::pagination with RFC 5988 Link headers, a default of 30 and a max of 100. GET JSON responses get weak ETags and If-None-Match→304. X-OAuth-Scopes and the X-RateLimit-* headers are set, media types (raw/html/diff/patch/sha/star/full/text) are parsed in bgh-repos, private resources return 404, and /meta reports a GHES version so gh's feature detection works. The gaps are mostly whole endpoint families that common tools call and get 404 for: GitHub Apps, deployments, repository_dispatch, commit comments, /markdown, /licenses, /gitignore, /repos/{o}/{r}/license, /stats, /traffic, /community, /repositories/{id}, and org rulesets. There are also some correctness bugs. Check-run, check-suite and combined-status lists return no Link header, PR-commit and commit-search node_ids differ from every other commit node_id, license detection never runs, and the `workflow` scope and workflow `permissions:` are never enforced. The GraphQL schema covers what gh needs (gh-compat passes), but the fields and mutations behind the Terraform provider (branchProtectionRules), the VS Code PR extension (timelineItems, addReaction, review-thread mutations), gh project and add-to-project (ProjectsV2 is a stub), and Backstage (membersWithRole, Team.members, Commit.history) are missing. Expected breakage by tool: the gh core flows work, but `gh repo create` templates, `gh repo license/gitignore`, `gh project`, `gh gist` and `gh secret --app dependabot` fail. Terraform's github_branch_protection and github_organization_ruleset fail. Flux githubdispatch and ArgoCD GitHub-deployment notifications fail, as does GitHub App auth in ArgoCD, Jenkins and Renovate. The VS Code PR extension (PR timeline, comments, reactions) and Desktop/GCM browser sign-in also fail. Renovate runs with GHE features off because there is no X-GitHub-Enterprise-Version header. Octokit paginate silently truncates check runs.

### [important/missing-feature] No GitHub Apps (app JWT, installations, installation access tokens)

GitHub exposes /app, /app/installations, /app/installations/{id}/access_tokens, /repos/{o}/{r}/installation, /user/installations and /installation/repositories, and uses ghs_ installation tokens. Many teams set up ArgoCD (repo creds and the ApplicationSet SCM provider), Jenkins GitHub Branch Source, Renovate (app mode), Flux and Backstage with GitHub App credentials. Jenkins only publishes Checks API results when it authenticates as an App. Here only classic PATs and OAuth-app tokens exist. Any integration configured as an App has to be rebuilt around a personal token.

*Area:* bgh-accounts, bgh-core::auth

*Evidence:* There are no `/app` or `installation` routes in any crate's router (I extracted every .route() path across crates/*). No docs mention GitHub Apps (grep -i 'github app|installation token' docs → none). The only authentication methods in bgh-core/src/auth.rs are token/bearer (bghp_/bgho_), basic and session.

### [important/security] `workflow` scope not enforced; GITHUB_TOKEN ignores workflow `permissions:`

GitHub rejects pushes or Contents API writes that touch .github/workflows/* unless the token has the `workflow` scope. It also narrows GITHUB_TOKEN to the job's `permissions:` block (contents: read, issues: write, ...). Here a plain `repo` token can rewrite workflows, which can exfiltrate secrets. Every job token gets Write on the repository no matter what the workflow declares, so least-privilege workflows silently get more access.

*Area:* bgh-core::perms/auth, bgh-repos (git_http, contents), bgh-actions

*Evidence:* In bgh-core/src/auth.rs:74 `"workflow" => false` is only a hierarchy entry. Nothing calls require_scope("workflow") (grep across crates). There are no .github/workflows checks in the bgh-repos push or contents paths. perms::effective (bgh-core/src/perms.rs:268-298) caps job tokens at Write or Read only. docs/packages/actions.md:157 says "`permissions:` is not applied to `GITHUB_TOKEN` (always repo-scoped Write)".

### [important/missing-feature] No fine-grained PATs (per-repository, per-permission tokens)

GitHub and GHES 3.10+ support github_pat_ tokens limited to selected repos with per-resource permissions (contents:read, pull_requests:write, ...). Many orgs require them by policy. Here tokens are classic only: a scope list and an expiry, with no repository selection and no organization approval.

*Area:* bgh-accounts::tokens, bgh-core::perms

*Evidence:* In bgh-accounts/src/tokens.rs, CreateTokenBody has only name/scopes/expires_in_days and the scope list is classic scopes only. There are no repository_ids or permissions fields, and nothing matches 'github_pat_' or 'fine.grained'.

### [nice/api-incompat] Conditional requests partial: no Last-Modified/If-Modified-Since, no X-Poll-Interval, 304s count against the rate limit

Only ETag/If-None-Match is supported, and only on 200 JSON GETs. GitHub also returns Last-Modified and honors If-Modified-Since. That is the documented polling protocol for /notifications, together with X-Poll-Interval. Raw, diff and contents responses get no validators. The rate-limit middleware runs inside the ETag layer, so 304 responses still consume quota; GitHub does not count them, which matters for polling CI and GitOps tools once enforcement is on. The ETag layer also buffers and SHA-256-hashes every JSON GET body, even when no If-None-Match was sent (large recursive trees and compares).

*Area:* bgh-server, bgh-core::ratelimit, bgh-notify

*Evidence:* bgh-server/src/lib.rs:234-284 etag() handles only If-None-Match and application/json. grep for last-modified, if-modified-since and x-poll-interval → none. Layer order in app(): .layer(ratelimit::middleware) is inside .layer(etag).
